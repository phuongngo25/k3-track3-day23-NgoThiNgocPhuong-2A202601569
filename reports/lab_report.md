## 2. Architecture

The workflow is a single `StateGraph(AgentState)` with **11 nodes** and **4 conditional edges**.
`docs/graph.mmd` holds the diagram exported straight from the compiled graph
(`make diagram` → `graph.get_graph().draw_mermaid()`).

```
START → intake → classify ─┬ simple       → answer ─────────────────────────→ finalize → END
                           ├ tool         → tool → evaluate ─┬ success → answer → finalize → END
                           │                                 └ needs_retry → retry ─┬ tool ↺
                           │                                                        └ dead_letter → finalize
                           ├ missing_info → clarify ────────────────────────→ finalize → END
                           ├ risky        → risky_action → approval ─┬ approved → tool → evaluate ↺
                           │                                         └ rejected → clarify → finalize
                           └ error        → retry ──────────────────────────→ (bounded loop above)
```

| Node | Responsibility | LLM |
|---|---|:--:|
| `intake` | Normalise the raw ticket text (provided example node) | – |
| `classify` | Intent classification into one of 5 routes | **yes — structured output** |
| `tool` | Mock support-API call; deterministic transient failure on the error route | – |
| `evaluate` | Retry gate: is this tool result actually usable? | **yes — LLM-as-judge (bonus)** |
| `answer` | Final customer reply, grounded strictly in the collected context | **yes** |
| `clarify` | Ask exactly one question instead of guessing | yes (+ template fallback) |
| `risky_action` | *Describe* the side effect; execute nothing | – |
| `approval` | Human-in-the-loop gate (mock by default, real `interrupt()` opt-in) | – |
| `retry` | Increment `attempt`, log the transient failure | – |
| `dead_letter` | Escalate once the retry budget is spent | – |
| `finalize` | Terminal audit event — every route passes through it | – |

**Design decisions worth calling out**

1. **Node names live in `routing.py`, not as string literals.** `graph.py` imports the same
   `N_*` constants the routers return, so a rename cannot silently desynchronise a conditional
   edge from its target. Each `add_conditional_edges` call also passes an explicit path map, so a
   router returning an unexpected name raises instead of dead-ending the run.
2. **Only one cycle exists** — `tool → evaluate → retry → tool` — and it is bounded by
   `route_after_retry` comparing `attempt` against `max_attempts`. A `recursion_limit` of 60 is
   set in the run config as a backstop, so a future wiring bug surfaces as a loud
   `GraphRecursionError` rather than an infinite run.
3. **`risky_action` is inert by design.** It writes `proposed_action` and nothing else. The only
   edge from that path into `tool` goes through `approval`, and `route_after_approval` treats a
   missing or falsy decision as *reject*. "Do not execute" is the default, not a behaviour that
   depends on a node remembering to check a flag.
4. **Classification is semantic, not lexical.** The classifier prompt encodes the priority order
   (risky > tool > missing_info > error > simple) plus the traps it implies — for example
   *"how do I delete my account?"* is `simple` (the user wants instructions) while *"delete this
   account"* is `risky` (the user wants an action). No scenario ID or exact query string appears
   anywhere in the code.
5. **Graceful degradation is explicit and visible.** Each LLM node catches provider failures,
   falls back to a deterministic path, and records both an `errors` entry
   (`classify_llm_unavailable: …`) and `mode="fallback"` in its audit event. `render_report()`
   detects those entries and prints a warning banner. A degraded run therefore *looks* degraded
   in the metrics instead of masquerading as a clean success — which is the whole point of having
   a fallback at all.

## 3. State schema

`AgentState` is a `TypedDict(total=False)` and every value is JSON-serialisable, so any
checkpointer backend can persist it without custom encoders.

| Field | Reducer | Why |
|---|---|---|
| `thread_id`, `scenario_id`, `query` | overwrite | run identity and input |
| `route` | overwrite | current route only — routing on a stale route would send the run down the wrong branch |
| `risk_level` | overwrite | current assessment; `high` is forced whenever the route is `risky` |
| `attempt`, `max_attempts` | overwrite | the retry budget must be a scalar the bound can compare |
| `evaluation_result` *(added)* | overwrite | `"success"` / `"needs_retry"`; the gate `route_after_evaluate` reads |
| `pending_question` *(added)* | overwrite | the clarification asked; also a success signal in `metric_from_state` |
| `proposed_action` *(added)* | overwrite | description of the pending side effect shown to the reviewer |
| `approval` *(added)* | overwrite | `ApprovalDecision` as a plain dict — read by `route_after_approval` |
| `classifier_mode` *(added)* | overwrite | `"llm"` or `"fallback"`; makes degradation auditable |
| `final_answer` | overwrite | the single reply that reaches the customer |
| `messages` | **append** (`operator.add`) | compact per-node trace |
| `tool_results` | **append** | the retry loop calls `tool` up to 3×; each attempt must add a row |
| `errors` | **append** | every transient failure and every LLM degradation is kept |
| `events` | **append** | the audit log metrics is computed from |

**Why the split matters.** The append-only fields are what make the retry loop safe: a node
returns `{"tool_results": [result]}` and the reducer concatenates, so no node ever needs to
read-modify-write a list — which would be a lost-update bug the moment two nodes touched the same
list. Conversely, making `route` or `attempt` append-only would break every router, because they
must read one scalar and not a growing history.

**One bug this schema caused, and the fix.** With the SQLite checkpointer wired in, the second
`make run-scenarios` reported *double* the nodes and retries of the first. Cause: `initial_state`
derives `thread_id` from the scenario ID, which is stable across runs, so the second run
*resumed* the first run's thread and the `add` reducers concatenated the old audit trail onto the
new one. Fix: `cli.scope_thread()` suffixes a per-invocation `run_id`
(`thread-S05_error-0d87dc41`), giving every run its own checkpoint lineage while keeping the
scenario identifiable in the thread name. This is exactly the class of bug that only appears once
persistence is real, which is why it is worth recording here.

### Why the numbers look like this

- **Node counts are path lengths, and they are stable.** `simple` and `missing_info` visit 4
  nodes; `tool` visits 6; `risky` visits 8; a twice-retried error path visits 10.
  `S07_dead_letter` visits only 5 because `max_attempts: 1` sends it to `dead_letter` on the
  first retry instead of looping.
- **5 retries, not 6.** `S05_error` and `S12_service_down` each retry twice (attempt 1 fails,
  attempt 2 fails, attempt 3 succeeds → 2 retry visits), while `S07_dead_letter` retries once and
  gives up. The failure window in `tool_node` is a function of `attempt` only — no randomness — so
  this count is identical on every run. That reproducibility is deliberate: a flaky retry count
  would make the metric useless as a regression signal.
- **3 interrupts = the 3 risky scenarios.** `S04`, `S06`, `S08`. Each has
  `approval_required: true` *and* `approval_observed: true`; `metric_from_state` fails any
  scenario that required approval but has `approval is None`, so a graph that skipped the gate
  could not score 100%.
- **`errors` is non-empty only on the three error scenarios**, where it holds the retry
  bookkeeping (`attempt 2/3 after transient failure: …`) — deliberately kept, because a run that
  recovered after two failures is not the same thing as a run that never failed, and the metrics
  should not flatten the two. All nine other scenarios have `errors: []`, which is what confirms
  no node fell back to a non-LLM path (§7).

## 5. Failure analysis

### 5.1 Transient tool failure → bounded retry (the loop that justifies LangGraph)

`tool_node` returns a string starting with `ERROR:` while `attempt < 2` on the error route.
`evaluate_node` refuses it deterministically (an `ERROR` prefix is never satisfactory, regardless
of what any judge says), `route_after_evaluate` sends the run to `retry`, `retry_or_fallback_node`
increments `attempt` and appends to `errors`, and `route_after_retry` decides whether to try again.

The bound is the whole point: `attempt < max_attempts` where `attempt` has *already* been
incremented, so attempt 3 of 3 means the budget is spent. Without that comparison the graph
cycles until the recursion limit and the customer gets nothing. This is also the concrete thing a
linear LCEL chain cannot express — the "am I done?" decision has to be an edge, not a step.

### 5.2 Unrecoverable failure → dead letter (`S07`)

With `max_attempts: 1`, the first retry exhausts the budget and `dead_letter_node` writes an
escalation reply naming the attempt count and the ticket ID. Two details matter:

- The customer still gets an answer. Silence is a worse failure mode than an honest escalation.
- `route` deliberately stays `error`. The *classification* was correct; landing in the dead letter
  is an outcome, not a reclassification. Overwriting `route` here would have made the scenario
  look like a routing failure in `metrics.json` — a metric lying about a correct decision.

### 5.3 Risky action executed without approval

The dangerous version of this graph is one where `risky_action` performs the refund and
`approval` merely logs it. Structural defences, in order of strength:

1. `risky_action_node` has no side effect at all; it only writes `proposed_action`.
2. The single edge from `risky_action` is to `approval` — there is no path that skips it.
3. `route_after_approval` reads `state.get("approval") or {}` and requires
   `.get("approved")` to be truthy. A `None` approval, a missing key, or a malformed dict all
   route to `clarify`. **Fail-closed by default.**
4. The rejection path is not a dead end: `clarify` explains that the action was not performed and
   asks what to do instead.

### 5.4 Vague ticket → clarification, not hallucination

`missing_info` never reaches `tool` or the grounded answer node. It asks one specific question
and terminates with `pending_question` set. `metric_from_state` counts a `pending_question` as
valid output precisely so the graph is not pushed into inventing an answer just to look
successful.

### 5.5 The LLM judge caught a bug in my own mock (found by running it for real)

On the first real-LLM run, `S05_error` did **not** recover as designed — it burned all 3 attempts
and dead-lettered. The cause was in `tool_node`, not in the graph: its success payload was a
generic shipping lookup (`status=shipped, carrier=DHL`), which is a coherent answer for a `tool`
ticket and nonsense for a *timeout report*. The heuristic evaluator accepted it, because
`"ERROR"` was not in the string. The LLM judge rejected it, because it does not address the
ticket — and the judge was right.

The fix was in the mock, not the gate: the error route now returns an incident-shaped recovery
result (`upstream support-api recovered on attempt 2, request reprocessed, root_cause=transient
upstream timeout`). `S05` then recovers on attempt 2 as intended.

This is the concrete argument for LLM-as-judge over a substring check. A substring check answers
"did the tool blow up?"; the judge answers "does this result actually help?" — and only the second
question catches a tool that fails *successfully*. It is also a caution: the judge is a real gate
with real teeth, so a sloppy tool contract turns into retries and dead letters rather than into
silently wrong answers. I would rather have that failure mode than the quiet one.

### 5.6 Reasoning-model response shape — the bug the fallback *hid*

The first real run reported 100% success, and it was still wrong. `classify_node` genuinely used
the LLM, but `answer_node` and `ask_clarification_node` fell back to templates on **10 of 12
scenarios**, with this in their `errors`:

```
answer_llm_unavailable: AttributeError: 'list' object has no attribute 'strip'
```

`gemini-3.6-flash` is a reasoning model, so langchain-core 1.x returns `content` as a *list of
content blocks* — `[{"type": "thinking", …}, {"type": "text", "text": "…"}]` — not a string.
`(response.content or str(response)).strip()` therefore raised, the `except` clause did its job,
and a template answer went out instead of a generated one.

Two lessons, and both cost me a re-run:

1. **A broad `except` around an LLM call buys availability at the price of silence.** The graph
   never crashed and the success rate never dipped, because `metric_from_state` only asks "right
   route, some output?" — neither of which the bug touched. What saved me was recording
   `mode="fallback"` and an `errors` entry *inside the metrics*, so the degradation was visible
   in a file I could grep. Had I only logged it to stderr, this would have shipped.
2. **`.content` is not the text.** The fix is `_message_text()`, which prefers LangChain's
   flattened `.text` and walks the block list as a fallback. Three unit tests now pin all three
   response shapes, so this cannot regress silently.

This is also why §7 reports which nodes ran on the LLM *per node* rather than quoting one
aggregate success rate. An aggregate would have hidden it again.

### 5.7 A status string leaked into a prompt — and the double-execution it exposed

With the LLM judge live, all three risky scenarios burned their entire retry budget and
dead-lettered, even though the approved action had *succeeded*. The `errors` trail showed why:

```
attempt 1/3 after transient failure: OK: executed approved action 'Requested side-effecting
  action: Delete customer account after support verification (risk_level=high).
  Not executed yet — awaiting human approval.' — status=completed
```

`risky_action_node` had baked lifecycle commentary into `proposed_action`
("Not executed yet — awaiting human approval"), and `tool_node` interpolated that whole string
into its success message. The result read *"executed approved action '…not executed yet…'"* — a
self-contradiction. The judge rejected it, correctly, every single time.

**Two distinct defects, one symptom:**

1. **Field discipline.** `proposed_action` is consumed by `tool_node` and by the answer prompt, so
   it must describe *the action* and nothing else. Lifecycle state belongs in the audit event.
   The fix reduced it to `"<query> (risk_level=high)"`, and a test now asserts that no word like
   "awaiting" or "not executed" can reappear there. This is the LLM-era version of a leaky
   abstraction: a string that was only ever meant for humans became part of a prompt.
2. **The retry loop was re-executing the side effect.** Independently of the judge being wrong,
   each retry re-entered `tool_node` with `approval.approved` still true — so the account
   deletion ran **four times**. That is the double-execution hazard I had listed as future work
   in §8, and persistence makes it *more* likely, not less. `tool_node` is now idempotent: it
   derives a key from `(thread_id, proposed_action)`, and if a prior result already carries that
   key it replays it and emits a `replayed` event instead of acting again.

I would not have found either one from the offline run: the heuristic evaluator accepted the
contradictory string, so the retry loop never engaged and the side effect never repeated. The
LLM judge is what turned a latent data-modelling mistake into a visible failure.

### 5.8 The classifier itself failing (the mode most likely to bite in production)

A wrong classification is silent — the graph runs perfectly down the wrong branch. Mitigations
in place: the priority order is stated explicitly in the prompt; structured output makes an
out-of-vocabulary route impossible (and an unknown value still falls back to `answer`, which
terminates); `route_after_classify` has an explicit default; and `S09_howto_delete` exists purely
to catch the "delete = risky" over-trigger in regression. What is **not** solved: there is no
confidence threshold and no escalation for low-confidence classifications — see §8.

## 6. Persistence / recovery evidence

`configs/lab.yaml` sets `checkpointer: sqlite` with `database_url: outputs/checkpoints.sqlite`.
`build_checkpointer("sqlite", …)` opens the connection with `check_same_thread=False` (LangGraph
may touch it from a worker thread) and sets `journal_mode=WAL` + `synchronous=NORMAL` — concurrent
readers during a run, without paying a full fsync per super-step.

### 6.1 Time travel — `make history`

`agent-lab history --scenario-id S05_error` runs the scenario and replays every checkpoint:

```
thread_id=thread-S05_error-0d87dc41  checkpoints=12
  step= -1  next=__start__      route=             attempt=0
  step=  0  next=intake         route=             attempt=0
  step=  1  next=classify       route=             attempt=0
  step=  2  next=retry          route=error        attempt=0
  step=  3  next=tool           route=error        attempt=1
  step=  4  next=evaluate       route=error        attempt=1
  step=  5  next=retry          route=error        attempt=1
  step=  6  next=tool           route=error        attempt=2
  step=  7  next=evaluate       route=error        attempt=2
  step=  8  next=answer         route=error        attempt=2
  step=  9  next=finalize       route=error        attempt=2
  step= 10  next=END            route=error        attempt=2
```

The retry loop is visible as state, not as a log line: `attempt` climbs 0 → 1 → 2 across the
`retry → tool → evaluate` cycle, and the run exits the loop the moment `evaluate` returns
`success`. Any of those 12 checkpoints can be forked and resumed.

### 6.2 Real crash recovery — `make demo-resume`

`agent-lab demo-resume` proves resume across a *process boundary*, not just within one graph
object:

- **Phase 1** — `LANGGRAPH_INTERRUPT=true`, so `approval_node` calls `interrupt()`. The graph
  halts with `next=('approval',)` and the interrupt payload (the proposed action) persisted.
- Then `del graph_a` — everything in memory is discarded. Only the SQLite file survives.
- **Phase 2** — a **fresh** `build_graph()` over the same file reads `get_state(config)` and
  recovers `next=('approval',)` from disk. Resuming with
  `Command(resume={"approved": True, "reviewer": "human-operator"})` completes the run: `tool`
  executes the approved action, `answer` grounds the reply on it, `finalize` closes the audit
  trail.

Recorded in `outputs/resume_evidence.json`:

```json
{
  "thread_id": "resume-S04_risky-57045243",
  "paused_at": ["approval"],
  "recovered_next_after_restart": ["approval"],
  "approval": {"approved": true, "reviewer": "human-operator", "comment": "resumed after restart"},
  "checkpoints_written": 10,
  "nodes_visited": ["intake","classify","risky_action","approval","tool","evaluate","answer","finalize"],
  "resumed_ok": true
}
```

`--reject` runs the mirror case: the resumed decision is `approved: false`, `tool` is never
reached, and the run ends through `clarify` — 8 checkpoints instead of 10.

`resume_success` in `metrics.json` is set **only** from this evidence file
(`cli._resume_success()` reads `resumed_ok`). A normal run can never flip it to `true`, so the
flag means what it claims to mean.

## 8. Improvement plan — what I would productionise first

1. **A confidence gate on classification.** Today a wrong route is silent (§5.8). I would have the
   classifier return a confidence score and send anything below a threshold to `clarify` instead
   of committing to a branch. Cheapest large win in real-world correctness.
2. **Exponential backoff with jitter in the retry loop.** `retry_or_fallback_node` currently
   retries immediately. Against a real API that is a thundering herd on the exact upstream that
   just failed. The state already carries `attempt`, so the delay is a one-line function of it.
3. **Idempotency keys — now partly done, and it needs to go further.** §5.7 caught a real 4×
   executed deletion, so `tool_node` now replays a recorded result instead of re-acting. But the
   key lives only in the result *string* and only within one run. Production needs the key on the
   outbound API call itself, scoped to the action rather than the thread, so a resumed run — or a
   duplicate ticket — cannot re-execute a refund either. Persistence makes double-execution *more*
   likely, not less, which is why this pairs with §6.
4. **Real approval transport.** `interrupt()` is the right mechanism, but the decision needs to
   arrive from Slack or a review queue with an authenticated reviewer identity and an audit
   record — `reviewer: "mock-reviewer"` must never be reachable in production. I would make the
   mock path fail loudly when an env flag marks the deployment as production.
5. **Parallel fan-out with `Send()`.** For tickets needing several independent lookups (order +
   shipping + billing), fan out concurrently and fan in on a reducer. `tool_results` is already
   append-only, so it is the correct merge point — the work is in the dispatch, not the state.
6. **Cost and token metrics.** `latency_ms` is captured per node, but not tokens or dollars.
   Per-node token accounting in the event metadata would show where the budget goes (my guess:
   `answer_node`, then the judge in `evaluate_node`) and whether the LLM judge earns its keep
   versus the substring check.
7. **A route-confusion matrix in the metrics.** `success_rate` collapses *which* route was
   confused for which. An expected-vs-actual matrix over a larger scenario set would show
   whether the classifier's errors cluster (e.g. `tool` bleeding into `simple`) and make prompt
   changes measurable rather than anecdotal.
